## 2. Architecture

```
 Discovery        QC            Canonical        Enrich        Content       Content QC     Image         Publish
 WF01 ───────▶ WF02 ───────▶ WF03 ───────▶ WF04 ───────▶ WF05 ───────▶ WF06 ───────▶ WF07 ───────▶ WF08
   │              │              │              │             │             │             │            │
   └──────────────┴──────────────┴──── Notion Master DB (single source of truth) ────────┴────────────┘
                                                   ▲ READ-ONLY
 Applicants (WhatsApp) ─▶ WF09 ─▶ Notion Leads DB (separate; never writes Master)
 WF10 monitors all run-logs / queue / errors; zero Notion writes; only R1 recovery + pruning on n8n Data Tables.
```

- Each workflow = one n8n JSON, generated by a Python builder (`workflows/WFxx/build_*.py`), inline Code-node JS extracted under `workflows/WFxx/src/` with local node tests.
- Shared infra: n8n Data Tables (logs, queue, dedup, state), Notion REST via Header Auth (not the built-in credential — see §14/B1).
- Hash chain: `fact_hash → Content Hash → Image Build Hash → Distribution Hash` (FNV in WF05–08). Any upstream change invalidates downstream approvals.
- See `ARCHITECTURE.md` for the short form.

## 3. Source of Truth

1. Notion Master DB = truth for jobs. Unknown ≠ No (never coerce).
2. Leads DB = truth for applicants (WF09 only writer).
3. n8n Data Tables = operational state only (queue, dedup, alert state, logs). Never business truth.
4. Workflow JSON + spec = truth for behaviour. If a spec and JSON disagree → JSON is what runs; log as inconsistency (do not silently fix).
5. gBizINFO is the mandatory company registry source (no token yet).

Ownership matrix: WF01 discovery · WF02 QC/company/Recruitability · WF03 canonical/dedup/lifecycle/tier · WF04 enrichment · WF05 content draft · WF06 content QC · WF07 image · WF08 publishing · WF09 leads · WF10 monitoring/recovery. A workflow must not write fields owned by another.

## 5. WF01–WF10 Detailed Contracts

The authoritative contract for each workflow is `specs/MTG_WFxx_Spec.md` (WF02/WF03: use `_V1.1` plus the V1.2 patch notes in §5.2/5.3 below). Summary of inputs/outputs/guarantees:

- **WF01 Scout** — IN: HelloWork source. OUT: new Master pages (Job ID auto-increment, status NEW). Gates M1–M8, Job Score ≥80, Company Score ≥90, dedup via `mtg_job_scout_cache`, CJK integrity check. AI: extraction + screening.
- **WF02 QC** — IN: NEW/unverified jobs. OUT: QC decision. gBizINFO lookup; registry failure ⇒ `REGISTRY_UNAVAILABLE` ⇒ REVIEW (never "not found"). AI may only LOWER a decision. Manual `Employer Verified` override honoured. Overseas-recruitment evidence must be explicit.
- **WF03 Canonical** — canonical key, dedup, lifecycle, tier (S/A/B/C), matching readiness. V1.2 = preservation patch (does not overwrite owner-edited fields). Idempotent.
- **WF04 Enrichment** — fills Unknown JLPT/License/Experience/Salary Basis: deterministic extraction first; AI only for remaining Unknown and value rejected unless exact verbatim quote exists in source.
- **WF05 Content** — factual rewrite with deterministic fallback; produces Content Hash; skips ineligible/insufficient-fact jobs. No publishing.
- **WF06 Content QC** — deterministic checks outrank AI second opinion; stale content rejected; max 3 attempts.
- **WF07 Image** — HTML/CSS poster (text NOT AI-generated), OCR verification, vision check, Image Build Hash, max 3 regenerations.
- **WF08 Distribution** — final gate. DRY_RUN default; hash-bound Legal Review (stale ⇒ block); `PUBLISHING` lock written BEFORE send (at-most-once); ambiguous result ⇒ `MANUAL_REVIEW`, never auto-retry.
- **WF09 Leads** — deterministic state machine; Lead Key = `sha256(salt|phone|JobID)[:24]`; AI classifies intent/language and can only escalate; draft-only (no send node); consent GRANTED only by documented rule; legal keywords ⇒ MANUAL_REVIEW; PII-masked logs; Leads `Lead Notes` never written; Master read-only.
- **WF10 Monitor** — read-only except R1 and prune. See §5.10.

### 5.2 WF02 / 5.3 WF03 version notes
`workflows/WF02/versions/` and `workflows/WF03/versions/` hold superseded JSONs. Current = WF02 V1.2, WF03 V1.2.

### 5.10 WF10 specifics
- R1: queue rows in `PUBLISHING` > 90 min ⇒ `MANUAL_REVIEW / AMBIGUOUS_PUBLISH` (approved by owner; **never auto-retry**).
- Findings catalog severity HIGH/WARN/INFO. Alert state in `mtg_monitor_state` (OPEN/RESOLVED; re-alert 12h HIGH / 48h WARN; heartbeat 24h row `__HEARTBEAT__`). One PII-free digest per run (`text` + `content` keys). `last_alerted` advances only after a 2xx webhook (or in log-only mode).
- PII guard: Leads query uses `filter_properties` limited to 8 columns (Lead ID, Lead Status, Status Changed, Last Contact, Purge After, PII Purged, Human Action, Draft Kind); refuses if any property id unresolved; discards responses with extra columns.
- Prune whitelist: DRY_RUN rows >7d, FAILED >60d, PUBLISHED only if `prune_published_days>0`, resolved state >14d. NEVER `PUBLISHING` / `MANUAL_REVIEW`. Default `prune_mode=DRY_RUN`.
- Config keys: see `config/WF10.config.example.json`.
